### F. Research and isolate the indexed-indirect API contract

This section records documentation/source research plus a microscopic Metal experiment. It does not reintroduce the rejected voxel renderer and does not supersede the measured visibility/culling hotspot above.

- [x] Confirm the branch is currently on Unity `6000.5.6f1` (`ProjectSettings/ProjectVersion.txt`).
- [x] Compare Unity's historical and current `Graphics.RenderPrimitivesIndexedIndirect` guidance. Unity 2021.2 explicitly said to pass the `SV_DrawID` semantic to `InitIndirectDrawArgs` for multi-draw support, but the current Unity 6 documentation removes that instruction and its own two-command example deliberately uses `InitIndirectDrawArgs(0)`, `GetCommandID(0)`, and `GetIndirectVertexID(svVertexID)`. The earlier `SV_DrawID` experiment therefore followed historical guidance that no longer describes Unity's current documented contract. Sources: https://docs.unity3d.com/kr/2021.2/ScriptReference/Graphics.RenderPrimitivesIndexedIndirect.html and https://docs.unity3d.com/ja/current/ScriptReference/Graphics.RenderPrimitivesIndexedIndirect.html.
- [x] Confirm Unity's documented indexed-addressing fields match the intended arena representation: `startIndex` selects the first index in the index buffer, while `baseVertexIndex` is documented as being added to values fetched from that index buffer. Source: https://docs.unity3d.com/cn/current/ScriptReference/GraphicsBuffer.IndirectDrawIndexedArgs.html.
- [x] Inspect a public mirror of Unity's `UnityIndirect.cginc`. For indexed draws, `GetIndirectVertexID(args, svVertexID)` returns `svVertexID` unchanged, while `GetIndirectVertexID_Base(args, svVertexID)` returns `svVertexID + args.startIndex`; it does **not** add `baseVertexIndex`. This proves candidate 1's use of `GetIndirectVertexID_Base` was the wrong correction for the voxel arena: it applied the index-buffer start as a vertex-buffer offset. Public mirror: https://github.com/chsxf/unity-built-in-shaders/blob/f8b371011a7021a1991c9b8bc8e0daf0b00de378/Shaders/CGIncludes/UnityIndirect.cginc. Caveat: the exact `6000.5.6f1` archive copy has not yet been directly diffed against this mirror.
- [x] Re-check the original bad commit `fbaf77b8d210cc5e5f98bd99c0bf50e8640a7ac2` against the current Unity example. Its command data used chunk-local indices with `startIndex = metadata.IndexStart` and `baseVertexIndex = metadata.VertexStart`, and its shader used `InitIndirectDrawArgs(0)` plus `GetIndirectVertexID(vertexID)`. That materially matches Unity's current documented shader pattern, so source inspection alone could not explain the Metal corruption.
- [x] Correct the terminology around the measured performance win. Unity issue UUM-91617 states that Multi Draw Indirect (MDI) is currently **not supported** and that Unity's documented multi-command APIs can produce multiple underlying draw calls even on APIs capable of native MDI. Therefore the ~390.66 FPS result demonstrates a valuable reduction in Unity/C# submission overhead, but it is not evidence that one native Metal MDI command was executed. Source: https://issuetracker.unity3d.com/issues/graphics-dot-rendermeshindirect-does-not-issue-multi-draw-rendering-commands-when-using-a-graphics-api-capable-of-multi-draw-commands.
- [x] Confirm the underlying optimization is not fundamentally prohibited by Metal. Apple's `MTLDrawIndexedPrimitivesIndirectArguments` natively contains `indexCount`, `instanceCount`, `indexStart`, `baseVertex`, and `baseInstance`, and Metal exposes indexed indirect drawing with that argument layout. The native API therefore supports the same conceptual split between an index-buffer range and a vertex base. Sources: https://developer.apple.com/documentation/metal/mtldrawindexedprimitivesindirectarguments and https://developer.apple.com/documentation/metal/mtl4rendercommandencoder/drawindexedprimitives%28primitivetype%3Aindextype%3Aindexbuffer%3Aindexbufferlength%3Aindirectbuffer%3A%29.
- [x] Confirm the corrected compute-written index arena target is supported by Unity. `GraphicsBuffer.Target.Index | GraphicsBuffer.Target.Raw` is explicitly documented as the combination for a buffer that serves both as a geometry index buffer and as a raw byte-address buffer in compute; an Index buffer stride may be 2 or 4 bytes. Thus the corrected `Raw | Index`, 4-byte arena is not itself an undocumented Metal workaround. Sources: https://docs.unity3d.com/cn/6000.0/ScriptReference/GraphicsBuffer.Target.html and https://docs.unity3d.com/ja/current/ScriptReference/GraphicsBuffer.Target.Index.html.
- [x] Record relevant Unity 6 API defects without conflating them with this Metal failure. UUM-136922 reports incorrect indices in `RenderPrimitivesIndexedIndirect` through `6000.5.0a7`, but its reproducer fails on Vulkan/DX11/DX12/OpenGL and explicitly does **not** reproduce on Metal, so it is evidence that the API has backend-specific indexing defects, not evidence for our exact bug. UUM-132672 reports `RenderPrimitivesIndexedIndirect` procedural instancing disabled in 6000.5-era builds and is fixed in `6000.6.0a4`; `6000.6.0a5` release notes call out the added procedural-instancing support. Sources: https://issuetracker.unity3d.com/issues/incorrect-indices-when-using-graphics-dot-renderprimitivesindexedargs-with-graphics-dot-renderprimitivesindexedindirect, https://issuetracker.unity3d.com/issues/procedural-rendering-is-disabled-when-using-graphics-dot-renderprimitivesindexedindirect, and https://unity.com/releases/editor/alpha/6000.6.0a5.

Draw the same command records twice: top row as `commandCount=4`, bottom row individually with `commandCount=1, startCommand=N`.
