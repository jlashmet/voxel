# Plan — VoxelShowcase Dragon Mesh Voxelization

## Acceptance / ownership
`VoxelShowcase` needs a reusable **authoring-time** conventional triangle-mesh → canonical voxel path, proved on a legitimately redistributable detailed curved winged dragon. Runtime must load/replay only baked sparse cells through normal voxel storage so rendering, collision, edits, and destruction share world truth. Matched source/voxel built-player evidence must be judged `production-quality`.

## Architecture / discriminator
Hypothesis A: `IStructureAuthoringSession` and normal structure storage remain authoritative; the missing capability is deterministic offline conversion plus composition wiring. Hypothesis B: an existing arbitrary mesh/SDF importer should be generalized. Result: **A supported; B rejected.** Generic implementation remains under `Structures/Runtime/MeshImport`: transformed triangles → conservative surface coverage → bounded closed-interior fill → deterministic material ownership → ordered sparse bake/codec → canonical authoring replay. Unity hierarchy/skinned adaptation is editor-only. Shared importer/metrics APIs contain no dragon/source/showcase policy, and independent non-dragon reuse is covered.

Input ownership is also separated: `StructurePlacementSelection` owns one-shot selection/commit state and `StructurePlacementInputRouter` owns control-consumption policy. Live `VoxelShowcase` call-site wiring remains incomplete because the connected whole-file writer cannot safely edit the large canonical scene owner from truncated reads; do not bypass this with reflection or a competing controller. Built-player feature proof must use the module-owned validation-scene architecture recorded for this issue rather than the Worldbuilding Gallery/top-level showcase as a test fixture; production integration still remains required by acceptance.

## Source / blockers
The user-provided `mountain_dragon_supported.zip` contains a 2,144,152-triangle CHITUBOX STL. Connectivity cleanup retained a 1,763,914-triangle dragon/scenic-base component. Deterministic 0.5-unit vertex clustering produced a conventional OBJ with 13,431 vertices / 29,734 triangles, 860,349 bytes, SHA-256 `f1f44d59f7d9c775b600ac0b9ad066a15a3c652bf685a12b2344b8c383ff12b1`, gzip SHA-256 `fd2f8253fcf5bc32b275640448511f59d20dcc7d01c307f99124b224431892d4`.

Repeated reconstruction failures are isolated to source-transfer packaging rather than the decoder. Run `33362323833` proved the historical segmented logical `part13` reconstructed to the wrong gzip identity. Run `33364246307` proved mixed whole+segmented transport fails closed as intended. After stale segments were removed, run `33364871767` proved the remaining whole `part13` is still malformed: the archive totals 319,999 Base64 characters rather than 320,000.

Because exact-source acceptance failed after materially different fixes, the transfer path was reduced to a minimal repro rather than mutated again. Historical/current repository variants are contradictory: the current 4,999-character `_probe13first5k` is an exact prefix of current `part13` but has Git-blob identity `ee2a84d752398b31be7d2c1f8c7884adee87dacd`, while historical `part13.00` is the different blob `d87618d052f83b18b0510951b2fef33b760f217b`. Independently staged `historical-part13.02` is 5,001 characters and the corresponding current window is that tail with one demonstrated deletion; repairing that deletion produces a 20,000-character `part13`, but the resulting complete gzip still does not match the pinned gzip/OBJ identities.

Exact-SHA CI run `33377081586`, job `99440882707`, passed `MountainDragonSourceArchiveTests.DiagnosePart13TransferLoss_HistoricalTransfersRemainNonAuthoritative`. This is the discriminator result: known repository history cannot establish a unique authoritative repair. Therefore source vendoring and any exact-source-derived bake remain externally blocked until the authoritative archive/source bytes are supplied or independently recovered. Acceptance is unchanged, the reconstruction adapter remains strict, and no further speculative source mutation is allowed.

Exact provenance is independently blocked: the user states the model was free and usable, but source URL, author, and named license/permission text are unavailable. Do not close licensing acceptance without them.

The STL/derived OBJ has no standard source material regions. Composition now deterministically maps unmaterialed source/interior cells to canonical `DarkStone` via `MountainDragonPalettePolicy`/`MountainDragonAuthoringPolicy`; this is explicit showcase palette mapping, not preservation of absent source color. Existing/future real source material IDs pass through unchanged.

## Current state / next work / gates
The shared importer now has explicit `VoxelShellFill` semantics independently covered by non-dragon topology regressions: topologically open input may fill only when conservative rasterization itself encloses voxel-space cells, while genuinely open rasters remain unfilled and `Reject`/`SurfaceOnly` semantics remain unchanged. The dragon composition explicitly opts into that policy at `0.30` source units/voxel with X/Z <=127, Y <=511 and no global thin-feature dilation.

Exact source vendoring, production bake generation, and dragon-anatomy assertions over that bake are blocked by the unavailable authoritative source bytes. Continue independent acceptance work instead of weakening those gates. The next independent implementation target is the canonical `VoxelShowcase` selection-mode wiring: reuse the existing `StructurePlacementSelection` and `StructurePlacementInputRouter`, keep ordinary movement/brush controls unchanged outside selection mode, and keep scene-specific policy in the canonical composition owner. Do not create a parallel controller or reflection authority. Comparison staging, module-owned validation scene, capture integration, metrics, and destruction validation follow where they can be implemented without pretending the final dragon artifact exists.
